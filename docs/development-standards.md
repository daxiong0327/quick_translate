## 基本要求

| 要求 | 执行方式 |
| --- | --- |
| 遵守编码规范 | 明确语言风格、命名、错误处理、取消、超时、资源释放及依赖规则 |
| 大任务拆为独立可测试任务 | 编码前定义结果、范围、依赖、接口、验收和恢复方式 |
| 每项任务进行审查和多层测试 | 保存审查结果与验证证据；不适用、未执行、失败、通过分别记录 |
| 达标后更新状态和提交 | 提交后为待合并；合入主分支且集成验证通过才完成 |
| 按依赖推进 | 前置任务合并后，从更新后的主分支开展后续任务 |
| 模块隔离 | 通过公开接口协作，由初始化入口注入配置与基础依赖 |
| 合理提取公共能力 | 仅提取有明确共享用途的基础能力，不在工具目录堆积业务逻辑 |

## M Fix 和 Task

新功能使用 `M → Task`，缺陷使用 `Fix → Task`。编号例如 `M001`、`Fix001`、`M001-T001`、`Fix001-T001`。创建前检查已有编号，创建后保持稳定。每个 Task 只属于一个父项，跨项关联使用依赖或引用。

记录按需保存于 `docs/tasks/milestones/`、`docs/tasks/fixes/` 和 `docs/tasks/tasks/`。M 记录目标、范围、整体流程验收、Task 清单和依赖；Fix 额外记录复现步骤、预期与实际行为、影响、根因及回归验收。

Task 必须记录目标、包含及不包含范围、所属项目和 Git 仓库、实际主分支、基线提交、开发分支、执行者、依赖、接口约定、运行环境、正常与异常验收条件、验证方式和恢复方式。接口契约在依赖它的实现开始前明确。

按可独立验证、可安全合并的业务结果拆任务，避免只拆“写界面”“写接口”而无法验收。未完成的能力不得暴露不能工作的入口；必要时默认关闭，无法隔离时重新拆分交付边界。

普通实现细节在既有授权内自主处理；重要产品歧义需澄清。新增范围通过任务体现，不静默改变既有验收标准。

## 状态和推进顺序

`待开始 → 实现中 → 审查中 → 验证中 → 待提交 → 待合并 → 已完成`

审查或验证失败后返回实现中修复，并重新验证受影响部分。阻塞记录原因、当前成果与解除条件，不把未执行当作通过。

检查通过才能进入待提交；提交成功仅进入待合并。合入实际主分支并通过集成验证，记录开发提交、合入主分支的提交和证据后，才能标记已完成。M 的全部必要 Task 合并且整体流程验收通过后才能关闭；Fix 还须证明原复现问题已解决。

互不依赖的任务可以并行，但须明确接口和文件责任；是否使用多个执行者遵守当前会话授权。不得把未完成的依赖声称为可用。

## 分支 提交和合并

1. 检查仓库、实际主分支、当前分支和已有修改。依据明确配置或远程默认分支识别主分支，不猜测名称，不把当前开发分支当成主分支。
2. 每个 Task 从实际主分支最新已确认提交创建独立分支，例如 `feat/m002-t001-settings`、`fix/fix001-t001-copy`；文档和维护任务使用携带 Task ID 的 `chore/` 分支。
3. 禁止直接在主分支实现任务，禁止从前一项未合并分支创建后续任务。有依赖的任务等待前置任务合并。
4. 保留已有修改，只暂存本任务文件；禁止无选择地暂存全部文件、强制重置、丢弃他人修改或重写主分支历史。提交说明包含 Task ID 和具体结果。
5. 主分支更新和合并冲突在开发分支处理。最终修改后重新审查、测试，再合并。默认普通合并，尊重已有仓库策略和 PR 要求。
6. 合并后检查主分支组合结果；失败则回到验证中或阻塞，记录已经合并的事实。后续修复从当前主分支创建修复分支并关联原 Task，不能直接修改主分支或重复合并已有提交冒充修复。

任务内的本地提交与本地合并不需要逐项重复确认，但不自动授权远程推送、发布、部署或付费服务操作。不存在仓库或无法识别主分支时，记录并处理前置条件，不伪造结果。

本项目首次规范迁移时目录为空、尚无 Git 仓库，文档先作为准备材料记录。2026-11-08 按用户要求建立本地仓库，依据已配置的默认分支名明确创建 `main`，再从空的初始基线创建文档任务分支。实际提交、合并和验收结果见 M001-T001 记录；后续任务继续按上述流程推进。

## 编码和模块边界

- 遵守实际语言与项目风格，职责集中，避免循环依赖、无依据的大型抽象和重复规则。注释解释约束和原因；修复针对根因。
- 模块通过窄的公开接口协作，不依赖其他模块私有结构，不绕过公开能力读写其数据。协调流程有明确归属。
- 初始化入口组装具体实现，按模块需要注入配置。允许常量和只读配置；禁止共享可变全局状态传递当前选区、翻译请求或业务状态。
- 系统事件监听、窗口、网络会话及后台任务的创建与释放必须明确，不在模块加载时隐式启动。处理取消、超时、并发和过期响应。
- 在边界校验选中文本、配置、外部响应和权限；UI 不承担协议解析规则，网络模块不决定窗口交互。
- 配置与凭据存储通过明确接口访问；按用户最新要求，API Key 仅写入本项目被 Git 忽略的 `.env`，不写入系统钥匙串、系统偏好、代码、任务记录或日志。原文与译文默认不持久化、不写日志。
- 依赖应有明确用途、版本和变更理由，优先使用项目已有能力。密钥、用户运行数据、构建缓存和签名私钥不得提交。
- 公共目录按日志、网络、系统适配等实际职责组织；业务规则留在业务模块。公共模块不得反向依赖业务模块，不为每个类型强行制造接口。

## 审查和验证

每个任务必须审查最终改动和验收条件。条件允许时独立审查；自行审查应如实记录。审查覆盖需求、范围、依赖、错误处理、权限、并发、资源释放、测试有效性及文档一致性。阻断正确性、安全或关键验收的问题必须关闭，其余意见记录处理结果或后续 Task。

| 验证维度 | 本工具的验证重点 |
| --- | --- |
| 单元测试 | 输入校验、请求状态、过期响应隔离、错误映射 |
| 集成测试 | 剪贴板适配、配置和凭据存储、协议解析、窗口事件 |
| 整体流程 | 真实应用选区、快捷键、真实阿里 API、原译文展示、点击外部关闭 |
| 边界异常 | 无选区、重复文本、权限拒绝、网络失败、长文本、并发触发、关闭后返回 |
| 回归验证 | 既有复制、设置、窗口交互和翻译能力不被破坏 |
| 覆盖率 | 真实工具、版本、统计范围、指标和未覆盖风险 |

按影响范围选择检查，避免只复述实现的测试。必要检查未执行或失败不得标为通过；最终修改后重跑受影响检查，共享模块和契约变更扩大回归范围。纯文档任务的代码运行测试和覆盖率可标为不适用，改为验证内容、引用和规则一致性。

外部服务替身可以验证失败路径与本地规则，不能代替真实 API 接入验收。自动化测试不能代替真实 macOS 应用的选区、权限、焦点和外部点击验证。缺陷修复需补充能发现原问题的回归验证。

覆盖率沿用普通业务 80%、核心规则 90% 的建议目标，尚非强制门槛；选型后说明实际工具支持的指标，不混用语句、行和分支覆盖率。记录真实基线、改动后结果、排除项及未覆盖风险，不通过缩小范围或跳过失败用例达标。关键验收路径必须单独验证。

## 交付标准和记录模板

进入待提交前，全部验收条件应有证据，阻断问题关闭，必要检查通过，不适用项有理由，文档与实现一致，无凭证或无关文件进入提交。合并后另行验证组合结果。

```text
Task ID 和名称：
所属 M 或 Fix：
所属项目与 Git 仓库：
实际主分支及基线提交：
开发分支：
目标与验收条件：
包含范围及不包含范围：
依赖和接口约定：
当前状态与执行者：
实现摘要：
审查方式、发现的问题及处理结果：
单元测试：
集成测试：
整体流程测试：
边界和异常测试：
回归验证：
覆盖率工具、范围、指标、结果、门槛和未覆盖部分：
验证环境与时间：
不适用或未执行项及原因：
数据迁移及恢复方式：
已知限制和后续任务：
开发提交编号：
合入主分支的提交编号：
合并后验证结果：
```

完成报告给出 Task ID、改动、审查、验证、分支、提交与合并结果和限制，不能混淆文件已生成、已测试、已提交、已合并与已发布。
